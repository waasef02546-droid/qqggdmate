一、先澄清文件名称与自动生效关系
--------------------------------

1. 真正会被 Codex 自动发现的是仓库根目录的 `AGENTS.md`，不是 `agens.txt`，
   也不是 `AGENS.md`。
2. 本文件 `agens.txt` 不会被 Codex 自动发现；它是“人类可读的设计说明、使用手册和主 Prompt 模板”。
   它用于解释为什么这样配置、在新任务中应该输入什么，以及哪些内容不应长期塞入
   `AGENTS.md`。它不会自动占用每一次任务的上下文。
3. `.agents/skills/presaga-paper-grade/SKILL.md` 是复杂工作流。需要论文级里程碑时，
   在任务中写 `$presaga-paper-grade` 即可显式调用。
4. `docs/workflow/current-milestone.md` 保存当前状态；测试历史在
   `docs/verification/test-ledger.yaml`；论文主张与证据映射在
   `docs/claims-evidence-matrix.md`。这些文件承担“外部记忆”，避免在对话中反复重述。

二、为什么不把所有内容都放进 AGENTS.md
--------------------------------------

`AGENTS.md` 每次任务都会进入上下文。若放入长篇背景、每个实验命令、论文全文和大量
示例，即使任务只是改一个小文件，也会持续消耗上下文和注意力。最终设计采用四层：

1. AGENTS.md：短、稳定、强约束。放使命、核心代码优先、验证去重、证据更新和并行边界。
2. Skill：只在论文/工程里程碑触发。放阶段流程、验收门、重测矩阵和自检方法。
3. 状态文档：只记录当前事实和历史证据，不把历史反复复制到 Prompt。
4. 本轮 Prompt：只填写变化的内容，例如本轮目标、授权范围和特殊限制。

这样减少的是“重复上下文、无边界探索和重复测试”，而不是减少必要的代码推理、
安全分析、实验验证或论文严谨性。

三、推荐的新任务主 Prompt
------------------------

把下面模板复制到仓库根目录启动的新任务中，只替换方括号。没有特殊限制的字段可以删掉。

使用 $presaga-paper-grade 推进 PRE-SAGA 的一个有界工作包。

工作包 ID：[例如 CORE-001]
目标：[一个可以验收的行为或研究结论]
本轮授权范围：[允许修改的模块、允许运行的实验、允许的外部访问]
明确非目标：[本轮不处理的内容]
必须达到的验收条件：
1. [核心行为]
2. [安全/失败行为]
3. [证据或论文映射]
特殊约束：[兼容性、时间、环境或依赖限制]

先读取 AGENTS.md、docs/workflow/current-milestone.md、
docs/verification/test-ledger.yaml 和 docs/claims-evidence-matrix.md。
可从本地文件或已配置工具查明的事实自行查明，不要让我重复提供。
先给出简短的工作包定义，然后直接实施；核心代码是主要产出。
测试只验证新增或改变的行为，先查测试台账，避免无理由重复运行。
只有存在至少两个相互独立的子任务时才并行，最多三个子 agent；
重叠代码区域只能有一个写入者。完成后迭代自检，直到验收门通过或出现有证据的阻塞。
最终只报告：核心改动、验证证据、论文/主张影响、剩余风险、建议的下一工作包。
不要未经允许自动进入下一工作包。

四、日常小任务的短 Prompt
------------------------

小修复不需要重复完整主 Prompt。使用：

按 AGENTS.md 处理：[具体任务]。范围仅限 [文件/模块]。若改变行为，运行最小相关验证并
更新测试台账；若不改变行为，不要重跑核心测试。

文献/论文审阅使用：

使用 $presaga-paper-grade，只做只读审阅：[具体问题]。把结论映射到现有代码、实验和
claims-evidence matrix；不要修改实现，除非我另行授权。

五、怎样提高效率而不牺牲论文质量
--------------------------------

1. 一次只推进一个工作包
   “完成整篇论文”没有明确停止条件，会造成长时间探索。工作包应是一个机制、一个
   攻击面、一个实验问题或一个可验证主张。

2. 先定义验收，再改代码
   验收至少包含：正常路径、拒绝/攻击路径、边界条件、可复现实验或证明、论文表述边界。
   这样不会在实现后才临时添加大量无目的测试。

3. 核心代码优先不是机械行数比例
   推荐工程里程碑把主要精力放在协议、Provider、策略、加密/存储或实验执行路径；
   测试和文档用于证明这些改变。不能为了“代码占比”删减必要验证，也不能用几十个
   重复测试掩盖核心机制没有推进。

4. 把历史事实写入文件
   已完成测试、命令、环境和证据路径写入 ledger；当前决策写入 milestone/ADR；
   主张写入 matrix。后续代理读取这些文件，不需要在 Prompt 中重复整段历史。

5. 工具按需启用
   官方 OpenAI Docs MCP 用于 Codex/MCP/Skill 配置。只有当某工作包确实需要实时库文档、
   GitHub 议题、外部数据库或设计文件时，才增加对应 MCP。每个长期 MCP 都会增加工具
   选择面；“可能有用”不足以成为安装理由。

6. 有界并行
   适合并行：代码只读探索、威胁审阅、独立组件实现、测试结果分析、证据审计。
   不适合并行：同一协议接口的设计与实现、同一文件写入、依赖前一决策的连续步骤。
   主 agent 保留架构和整合；子 agent 只返回结论与文件位置，不返回整段日志。

六、思考与迭代怎样形成
----------------------

工作流不是要求模型展示冗长“思维过程”，而是用可观察产物构成闭环：

需求/论文主张
  -> 有界工作包与验收条件
  -> 设计影响与风险
  -> 核心代码实现
  -> 按变更影响选择验证
  -> 记录证据
  -> 对照验收门自检
  -> 未通过则修正同一工作包
  -> 通过后更新主张与限制
  -> 等待用户授权下一工作包

每轮自检只回答可验证的问题：

- 行为是否真的由核心实现提供，而不是只由测试模拟？
- 拒绝路径是否由服务端/协议层强制，而不是调用者自觉？
- 安全主张是否超过了当前 toy PRE、HPKE stub 或实验环境的能力？
- 测试是否针对本轮变化？是否已有等价成功记录？
- 论文文字、代码、实验、形式化结果是否指向同一属性？
- 是否存在无法复现、无路径、无命令或无环境说明的“证据”？

若答案为否，就在同一工作包内迭代；若是，就停止并请求下一阶段决定。这里的“停止”
是防止范围漂移，不是降低完成度。

七、MCP 的实际配置说明
----------------------

当前官方文档 MCP 使用：

    [mcp_servers.openaideveloperdocs]
    url = "https://developers.openai.com/mcp"

这是公开的 Streamable HTTP 文档服务，不需要 token、token URL、OAuth callback 或
Bearer Token。设置界面中的这些字段是为“需要认证的其他 MCP”准备的，留空即可。
只有服务提供方明确给出 OAuth 或环境变量 Token 时才填写：

- url：MCP 服务地址；
- bearer_token_env_var：保存 Token 的环境变量名称，不是 Token 本身；
- OAuth/token URL：仅在服务提供方要求 OAuth 时使用；
- command/args：仅用于本地 STDIO MCP，与 HTTP URL 二选一。

全局配置位于用户 Codex 配置中，所有仓库可用；仓库 `.codex/config.toml` 只保存本项目
的多 agent 策略，避免复制同一个全局 MCP。

八、简单验证任务与预期
----------------------

实际验证命令应从仓库根目录启动一个新 Codex 任务，因为 AGENTS.md 在任务启动时加载：

    codex exec --sandbox read-only --ask-for-approval never
      "使用 $presaga-paper-grade。只读取控制文件，不改文件。用不超过 8 行报告：
       当前工作包、核心代码优先规则、何时并行、何时不重复测试、完成停止条件。"

合格结果：

1. 能识别 current-milestone；
2. 明确测试不能替代核心实现；
3. 只在独立任务存在时并行且不超过三个子 agent；
4. 先查 ledger，再决定是否重测；
5. 不擅自开始下一工作包；
6. 回答简短，没有展开无关论文背景或运行全套测试。

结果解释：

- “输出简短、没有无关工具调用、没有多余测试或子 agent”可以验证行为效率。
- 单次命令显示的 tokens used 不能单独证明 Token 已降低；必须有同模型、同仓库、
  同任务和同环境的基线才能比较。
- 若行为验收已通过而没有研究价值明确的对照问题，不应仅为了获得一个更小数字重复调用。
- `CFG-001` 的实测为 6 行、1,744 ms、报告 20,402 tokens：行为效率通过，绝对 Token
  降低未量化，因此不作过度结论。

仓库结构自检命令：

    python .agents/skills/presaga-paper-grade/scripts/check_repo_workflow.py --root .

该检查只验证指导层结构，不替代功能测试。指导文件发生变化时运行它；核心代码未变化时
不应因此重跑项目全套测试。

九、需要用户决定的工作流问题
----------------------------

完成本次仓库级配置后，需要你确认下一阶段采用哪一种推进方式：

A. 推荐：先选择一个最高优先级核心工作包，主 agent 定义验收并实施；只有独立的只读
   审计/验证任务使用子 agent。
B. 每个里程碑固定三路并行：核心实现、安全审计、证据/论文同步。速度可能更快，但
   token 与协调成本更高。
C. 先做一次全仓库只读审计，形成完整路线图，再开始核心实现。前期更稳，但会延后代码
   推进。

若没有额外偏好，推荐 A。
